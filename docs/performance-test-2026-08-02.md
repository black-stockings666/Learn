## 4. 结论与建议

本轮共完成 17 个场景、1,169,759 次请求，全部返回 HTTP 200，未出现连接错误、超时或 4xx/5xx。

- 热门视频吞吐在约 1,850～2,000 QPS 的平台区间内；100 并发时 P99 为 62.04 ms，200 并发升至 131.53 ms，800 并发为 574.34 ms。若目标为 `P99 < 100 ms`，建议该路径单实例控制在约 100 并发。
- 视频列表在 100～200 并发达到约 3,300 QPS；100 并发 P99 为 64.61 ms，200 并发为 171.88 ms。若目标为 `P99 < 150 ms`，建议控制在约 100 并发。
- 更接近日常使用的混合流量中，200 并发持续 60 秒达到 3,057.65 QPS、P99 144.94 ms；400 并发仍无错误，但 P99 增至 192.27 ms。因此当前本机、小数据量、热缓存条件下，可将约 200 并发 / 3,000 QPS 视为 `P99 < 150 ms` 的保守读接口基线。
- 本机发压、同机部署、少量测试数据及热缓存会高估生产能力。生产复测应使用独立发压机、接近生产的数据规模与至少 10～30 分钟的持续混合流量；登录和各类写接口应在隔离数据集内单独压测。

## 5. 复现方式

```powershell
# 如宿主机已占用 3306，使用此压测覆盖配置启动服务；它不会暴露 MySQL 端口。
docker compose -f docker-compose.yml -f docker-compose.benchmark.yml up -d

# 完整套件：约 7 分钟
node scripts/run-performance-suite.js

# 快速回归：约 100 秒
node scripts/run-performance-suite.js --quick

# 指向其它环境，并把报告写到指定位置
node scripts/run-performance-suite.js --base-url "http://127.0.0.1" --backend-url "http://127.0.0.1:8080" --report "docs/performance-test-2026-08-02.md"
```

脚本会先请求 `/api/videos/hot?limit=1` 进行健康预检；预检失败时不会开始发压。
